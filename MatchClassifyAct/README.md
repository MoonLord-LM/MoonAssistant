# MatchClassifyAct（MCA）

> **Match the pixels, Classify the state, Act accordingly.**
> 匹配像素 → 分类标注 → 执行动作。

Spring Boot 3.2.5 + JDK 17 + JNA 的 Windows **图形程序自动化**工程：对任意 GUI 窗口做「后台截图 → 人工给画面状态打标 → 实时识别当前画面属于哪个状态 → 按定义发送鼠标点击」。默认演示目标是 MuMu 模拟器内的安卓程序，改配置即可自动化任意窗口。

```
截图（窗口内容） → 分类标注（人工，控制台） → 对照图产物（汇总分析）
                                              ↓
                            执行模式：实时画面比对识别 → 鼠标点击
```

---

## 一、快速开始

前置：JDK 17 + Maven；须在**真实桌面会话**运行（无桌面环境抓不到窗口）。

```powershell
mvn -DskipTests package
java -Dfile.encoding=UTF-8 -jar target/MatchClassifyAct-0.0.1-SNAPSHOT.jar
```

- 启动就绪后自动以 Edge/Chrome 应用窗口打开控制台（`http://localhost:8080/annotate`，`--ui.auto-open=false` 可关）；页面会持续探测后端，检测到代码更新后**自动刷新**加载新版。
- 自动采集（截图）**默认不开启**，需在页面右上角点「自动采集」；右上角「完全退出」结束服务并自动关页。
- 日常重启用 `restart.cmd`（停旧进程 → 清 `target\` → 重新打包 → 启动，日志在 `log\`）；`stop&clean.cmd` 只停并清构建输出。
- 数据都在运行目录下的 `resource\` 里（四个分区 `capture` / `classify` / `summary` / `runtime`，可整个 `resource\` 一起拷贝/备份），启动自动创建；**可随时整目录拷贝/备份**。

## 二、目录与数据流

| 目录 | 内容 |
|------|------|
| `resource/capture/` | 后台采集的**原始截图**（未标注，`IMG_yyyyMMdd_HHmmss_SSS.png`） |
| `resource/classify/` | 保存标注时图从 resource/capture/ 移入；图旁同名 json **只记归属** `{"state":…}`；`data.json` = **分类定义中心表**（每分类一份动作+坐标） |
| `resource/summary/<分类标注>/` | **汇总分析产物**：对照图（15 张基础合成图 = 交集六档 same100/90/80/70/60/50（100% = 样本像素完全一致，其余覆盖 >90%/80%/70%/60%/50%）与多数/均值/去重均值/8·32 块图族；每张基础图各带 1 张 `-unique` 独有区图，共 15 张——基础图与独有区图**全部参与识别比对**；每个分类以**注意点**（未设 = 屏幕中心）为中心另含 12 张**注意区交集图** = 1/8、1/32 方框 × 交集六档，鼠标点击分类再以**点击点**为中心另有 12 张**点击区交集图**，同样全部参与比对）+ `info.json`，供人工目检与算法调优 / 特征验证读取，可随时整目录删除后重算 |
| `resource/summary/_all_/` | 汇总分析列表**固定第一条「全部」**的产物：**12 张** = 交集图 6 张（`same100.png` 100% 档 = resource/classify/ 全部已标注截图的**公共部分**、`same90/80/70/60/50.png` = 每像素取一致张数 >90/80/70/60/50% 的**稳定区**）+ 多数 / 均值 / 去重均值 3 张代表图（`major.png` 多数图、`avg.png` 均值图、`dedup-avg.png` 去重均值图）+ 这 3 族「**与代表图差异最大的一张原图**」（`<kind>-maxdiff.png`，直接复制命中的原图 PNG，不重编码）+ `info.json`（`items` 记 12 张的角标与命中原图名：交集族角标 = 覆盖像素占比，其余族代表图 = 全部原图与该图的平均差异）；不做分类分组、不参与识别比对，仅供整体目检（分类标注若与「全部」同名，目录名自动加 `_cls` 后缀，两者互不影响） |
| `resource/classify/dedup-cache.json` | 启动历史重复清理的**比对结果缓存**（在 `resource/classify/` 里与已标注截图同目录，可随时删除，删了只是下次多算一遍；旧版放在运行目录根下的同名文件首次访问时自动搬入）：JSON 记录「互相比较过的文件组」，形如 `{"version": 1, "pairs": { "IMG_a.png@<mtime>": { "IMG_b.png@<mtime>": 不一致像素点占比 } }}`——每对图只记一条（两侧身份按字典序、小的作外层键），所以**每个文件组独占一行**、可直接查看与裁剪；四元组都没变过的组合下次启动**直接复用、不再逐像素比对**，已删除文件的条目在下次清理时自动裁掉 |
| `resource/summary/opt-result.json` | 「算法调优」结果的**完整缓存**（可随时删除，删了回到「未计算」；随 `*.json` 一并被 git 忽略）：形如 `{"version":1,"fp":"<验证指纹>","sig":"<算法结构签名>","savedMs":…,"samples":…,"groups":…,"result":{…各算法结果 + 逐分类明细…},"tune":{…最近一次自动调整参数摘要…}}`——进程启动首次访问算法调优（或 `tunable()`）时若文件在、且 `fp`（已标注 + 汇总分析没变）与 `sig`（算法组合口径没变、特征验证结果都还新鲜）都对得上，就直接恢复上次结果与调整摘要（界面显示上次结果，无需重算）；对不上即标记为需重算（界面照样展示上次结果 + 主图区顶部一条「需重算」状态条，见 3.5）并提示重新计算。写盘同样先写 `.tmp` 再原子改名；摘要里的 `file` 字段记的是权重文件**相对运行目录**的位置（`StoragePaths#classifyFile` 按配置给出，如 `resource\classify\opt-weights.json`），不写本机绝对路径 |
| `resource/summary/verify-matrix.json` | 「特征验证 / 算法调优」共用的**逐图比对结果缓存**（可随时删除，删了只是重算一遍；随 `*.json` 一并被 git 忽略）：形如 `{"version":1,"fp":…,"savedMs":…,"kinds":{"same90":{"cols":[[state,w,h,attnLeft,attnTop,actLeft,actTop,产物mtime,产物size,info.json mtime,info.json size],…],"decoded":[…],"valid":[…],"rows":{"img_0001.png":[mtime,size,w,h,[与各分类的不匹配占比…]],…}},…}}`——两层键：**列**（该特征在每个分类目录下的产物与 `info.json` 的大小 + 修改时间，外加尺寸 / 注意点 / 点击点）对得上就说明产物像素与裁剪框心没变、**整表照用**（连「该分类有没有有效产物」也照用，一个 PNG 都不解码）；**行**（原图文件名 + 大小 + 修改时间 + 所属分类宽高）对得上就**直接取用该行分值**（连原图都不解码），只有真正变过的那部分重算。分值按双精度原样写盘（可无损读回，保证「并列」判定与重算完全一致）；比对口径（`compareKind` / 裁剪）改了要 bump 文件里的 `version`，否则旧数值会被当成新口径复用。特征验证一次完整跑完（无中断）后与 `verify.json` 一起落盘（先写 `.tmp` 再原子改名）；算法调优 `prepare()` 的矩阵读的是同一份、特征验证刚跑完就直接在内存里命中 |
| `resource/summary/opt-weights.json` | 「算法调优」的**特征选择 + 权重数值快照**（每次「刷新算法特征 / 自动调整参数」跑完覆写一份最新的，可随时删除）：形如 `{"version":1,"fp":…,"sig":…,"algos":[{"id":…,"name":…,"tunable":…,"features":[{"kind":…,"x":…,"a":…,"b":…,"c":…,"e":…,"other":…,"why":…}],"weights":[…],"accuracy":…,"tieRate":…}]}`——`features[].kind`（特征选择）与 `weights`（权重 Y，0~10、精度 **0.001**）**一一对应**，含当时指标，供后续功能（例如执行模式）与开发验证直接读取，不必解析界面状态；它与上面 `resource/classify/opt-weights.json`（界面可调 Y 的持久化，单一特征算法不写）是两份不同用途的文件；进程启动恢复上次结果时也会顺带读它的 `algos`，作为「过期态照常展示上次算法结构」的数据源（见 3.5） |
| `resource/classify/opt-weights.json` | 「算法调优」落盘的**当前生效权重**（同样在 `resource/classify/` 里，可随时删除、删了回到默认全 1；**「刷新算法特征」与「自动调整参数」跑完都会写**，文件始终 = 最近一次算过的权重）：形如 `{"version": 1, "algos": { "<算法id>": { "kinds": ["same100", …], "y": [0.37, 1, …] } }}`——`kinds` 记特征顺序、与 `y` 一一对应（特征集合变了这条自动作废、按全 1 处理）；`y` 为 0~10 的权重、**精度 0.001**（手写更多位数读出时按 0.001 收齐）；界面上的权重输入框以这份文件为起点（改完文件刷新页面即生效），点「刷新算法特征」时把本次算过的权重一次写全（只写这次算过的算法、值没变就不重写），点「自动调整参数」时每采纳一处调整就原子重写一次（都先写 `.tmp` 再改名）。单一特征算法不写进文件（权重恒为 1） |
| `resource/runtime/` | **运行时算法**（算法调优每次跑完自动重刷，可随时整目录删除 —— 删了执行模式与「未标注」的智能推荐就提示「请先完成算法调优」）：`algorithm.json` 记本轮选出的**综合最佳算法**（`features` = 特征 kind + 基础分 X + 生效权重 Y，按序一一对应；`states` = 各分类的标注名 / 动作 / 点击坐标 / 分辨率 / 目录名），另含 `algoId` `algoName` `accuracy`（匹配正确率）`tieRate`（无法区分率）`score`（综合分 =（1 − 无法区分率）× 匹配正确率）`source`（`verify` = 刷新算法特征 / `tune` = 自动调整参数）`builtMs` `costMs`；同目录下 `resource/runtime/<分类>/` 放**该算法用到的**那几种 kind 的产物（文件与 `resource/summary/<分类>/` 同名，从那里**复制**过来 —— 复制而非搬走，`resource/summary/` 仍要留给特征验证 / 人工目检，内容没变的文件不重写、只覆盖变了的那几个），`info.json` 不复制（动作 / 坐标已进 `algorithm.json`）。 |


数据布局例子：

```json
// resource/classify/data.json   —— 分类级统一定义（动作 / 点击点 / 注意点只存这里）
// click 分类：left/top = 点击点（执行时真正点击、必填）；attnLeft/attnTop = 注意点（可选，不写或写 null = 默认屏幕中心）
{ "登录页": { "action": "click", "left": 640, "top": 360, "attnLeft": 500, "attnTop": 300 } }
// 无动作分类：没有点击点，只有注意点（可选，不写或写 null = 默认屏幕中心）
{ "等待中": { "action": "none", "attnLeft": 640, "attnTop": 360 } }
// resource/classify/IMG_xxx.json —— 每张样本只写归属
{ "state": "登录页" }
```

## 三、控制台使用

左上角「工作模式」下拉在 **标注模式 / 执行模式** 间切换。

### 3.1 标注模式（打样本）

顶栏六段导航：**未标注 / 已标注 / 全部 / 汇总分析 / 特征验证 / 算法调优**（2026-09-13 由「全部 / 未标注 / 已标注 / …」调整为「未标注 / 已标注 / 全部 / …」，「全部」= 浏览 + 分类过滤用的视图，退到第三位；**页面启动默认停在「未标注」**，与第一个标签一致）。流程：看图 → 填分类标注 → 定匹配动作与点 → 保存并下一张。

- **分类标注** = 画面状态名（登录页 / 主界面 / 弹窗…）。它同时用作汇总产物目录名，故不能含 `\ / : * ? " < > |` 等文件名非法符号（输入时自动剔除）。chip 上的 ✎ 可整体改名（中心表 key 与全部样本归属一并更新，旧产物目录自动清理）。
- **匹配动作** = 无动作 / 鼠标点击，每类各带 **2 个点（双点，编辑面板分三行：分类标注 / 动作 / 点击点·注意点·清除注意点）**：
  - **点击点**（红点）= 执行模式真正点击的位置，仅「鼠标点击」分类有、必填；也是**点击区交集图**的框心。
  - **注意点**（绿点）= **注意区交集图**与识别裁剪的中心，任何分类都可设置；**未设 = 默认屏幕中心**（所有分类一致，不再回退点击点），鼠标点击分类的注意点可与点击点分别设置。
  - 图上用 `点击点 / 注意点` 切换按钮选择当前编辑哪个点，再在图上点一下即可落入该点；只切换编辑目标不算修改，点「清除注意点」才标记为修改（清除后该分类的注意点恢复默认屏幕中心）。
- 每个分类只有一份定义：**首次**打标时确定，之后同分类加样本直接填分类保存即可，坐标自动沿用；在已标注图上改动作 / 点击点 / 注意点 = **重定义该分类**（全组同步，保存前会提示旧定义与新定义的差异）。唯一动作只约束**仍在使用（有样本）**的分类；样本删光后中心表残留的空定义视为全新分类，下次首标会直接重新定义，不会挡你新建。
- 保存后自动带出上次标记并跳到未标注图，快捷键 `↑`/`↓` 切图、`Enter` 保存，可连续快速打标。
- 「已标注」视图里点标签右侧的数字 = 只浏览该分类的已标注图并跳到第一张（再次点击同一数字取消过滤），不会跳去「全部」。
- 左侧列表排序：全部、已标注按时间倒序（最新在上）；未标注按时间正序（最早在上），从最早的开始逐张往下打标。
- **图片像素 = 窗口坐标**（截图即窗口内容，resize 已逐像素对齐），坐标语义一直沿用到执行点击。

### 3.2 后台截图与去重

- 页面点「自动采集」后按 `capture.interval-ms`（默认 1s）周期后台截图，节拍是 **fixedDelay**：处理完一帧再等这么久取下一帧，绝不叠帧。
- 每帧保存前与历史全部 PNG（resource/capture/ + resource/classify/）全尺寸逐像素比对、统计不一致像素点占比，须与每一张都 > `capture.diff-threshold-percent`（默认 5%）才保存，否则判为重复丢弃；结果以单条轻提示展示在右下角（保存成功 / 与哪张重复）。
- **每次启动**还会在后台自动清理一遍历史重复（自动截图与手动去重任一开启即执行）：按两个启用阈值中较低者（默认 min(5, 1) = 1%）逐像素比对，只删与保留图不一致像素占比 ≤ 阈值、几乎重复的截图（近似但不相同的画面一律保留），避免误删；画面持续变化产生的新重复仍靠运行期去重挡。清理结果（无论有无删除）在右下角提示一次、并完整进「历史日志」：含参与张数、删除张数、**实际全尺寸比对次数**、**其中复用缓存省掉的次数**与**最低的不一致像素占比**（= 最接近重复的一对还差多少，未删除时据此判断离阈值有多远；无可比对的同尺寸图时省略该段）与耗时。
- 每次的比对结果都按**两张图的文件名 + 最后修改时间**四元组持久缓存在 `resource/classify/dedup-cache.json`（与已标注截图同目录，JSON「互相比较过的文件组」）：四元组都没变过的组合下次启动**直接复用、不再逐像素重算**（所以全量重扫过一遍后，重启几乎瞬时完成、连 PNG 都不必再解码）；缓存的是**差异值**而不是「是否重复」，判定仍拿本次阈值去比，改阈值 / 文件内容变了（mtime 变 → 该条自动失效）都不会用错或漏算；缓存条目按本次枚举到的截图集合裁剪（已删除文件的条目丢掉），不会随历史无限增长，文件本身也可随时删除。
- 这次清理**开始 / 进行中 / 结束各有一条消息**（历史全量逐像素比对可能持续较久，避免看起来像卡住）：开始时右下角提示一条「启动重复清理：开始检查 resource/capture/ 与 resource/classify/ 的历史截图是否重复，逐张全尺寸逐像素比对，…请稍候…」；进行中显示一条**一直刷新**的进度消息——`正在检查重复图片：849/877 张，当前文件名：IMG_xxx.png，已耗时 8 秒，逐像素比对 42 个，复用历史比对结果 359128 个`，**逗号串联、不套括号**（用户 2026-09-13 指定；段与段用「，」，无当前文件名 / 无判定量时整段省略），已耗时**逐秒走动**（后端逐张写进行态快照、`GET /api/app/meta` 的 `startupDedup` 下发，页面每 2 秒取一份 + 本地 1 秒 ticker 复现）；这条常驻进度**不占右下角**，只显示在「未标注」页面最下方那条 tips 行里（见 3.3 开头「全局底部 tips 行」；扫描期间顶栏「未标注」标签同步转黄），也**不入「历史日志」**（避免每张一条刷屏）；结束后进度消息撤掉、由上面那条结果提示收尾。这条进行态文案由前端 `dedupProgText()` 单独拼接（**不走 `progLine()` 的括号模板**）；控制台里其余「长任务进行中」提示（汇总分析的清场 / 统计待分析组合 / 生成对照图，见 3.3）仍用 `progLine()` 那套括号写法。
- 截图目标尺寸不符 `capture.resize-width × resize-height`（默认 1280×720）时，自动用 `SetWindowPos` 缩放窗口后重截验证，直到 PNG 恰好达标才保存。

### 3.3 汇总分析（生成对照图）

> **全局底部 tips 行（`#tipsBar`）**：每个页面（六个视图 / 执行模式各自）最下方固定留出一行 30px 的常驻进度区，靠左一行小字显示「现在在干什么、到哪了」，超长省略；**进度文本可用鼠标选中 / 复制**（不拦鼠标、光标为文本光标）。**本页没有常驻任务时不显示任何文本**（元素不隐藏、宽高恒定：仍占满最下 30px 与整屏宽，只剩一条上边框 + 面板底色，起分隔线的作用；也没有悬停提示）。
> **进度不汇聚，各页只显示自己的那条**（用户 2026-09-13 指定）：谁的任务归哪一页由 `TIPS_VIEW` 定死 —— 启动重复清理 → 未标注（见 3.2）、汇总分析 → 汇总分析（本节）、特征验证 → 特征验证（3.4）、算法调优 → 算法调优（3.5）；切页面时 tips 行随之改显示目标页自己的进度（`tipsRender()` 在视图 / 模式切换处调用）。

### 3.4 特征验证（第 5 视图，挑特征）

左栏列出**全部 kind**（顺序 = `FrameClassifier.verifyOrder()`，不另写清单），每行 = 状态 chip + **只给两个数：D 匹配正确率 · E 无法区分率**（A/B/C 与样本数只在主图区的汇总卡与明细表里）；主图区给出**五个**指标的汇总卡与逐分类明细表（分类 / 匹配动作 / 自分类平均 / 是否生成成功 / 匹配正确率 / 匹配正确分类的个数 / 无法区分率 / 无法区分的个数）；右栏是说明 + 「开始验证」+ 进度。左栏过滤按钮固定两个：`生成成功率100%`（A ≥ 100）与 `匹配正确率80+%`（D ≥ 80）。

- **A 生成成功率** = 能生成有效合成图（产物存在且非全透明空图）的分类数 / 参与分类数：越高说明该算法适用的分类越多。
- **B 自分类平均匹配值** = 有效分类样本「与自家产物」匹配像素占比（= 100 − 不匹配占比）的平均值：越高说明该特征对本分类越稳定。
- **C 其它分类平均匹配值** = 有效分类样本「与其它分类产物」匹配像素占比的平均值：**越低越好**，越低说明越能把它与别的分类分开。
- **D 匹配正确率** = 在能生成有效图的分类里，原图与「所有分类的该算法生成图」比对、最佳命中**唯一最高**且**恰好是自己分类**的占比；**无法生成有效图的不参与统计，无法给出最高值的结果（最高分被 ≥2 个分类并列、分值一样、分不出该选哪一类）的也不参与统计**（这些样本只计入 E）→ 分母 = 可匹配样本数 − 无法区分数（= 命中 + 误判）。D 卡副标题写「（可匹配样本 N 张，其中能给出结果 K 张）」。D 告警色：低于 50 红、低于 90 黄。
- **E 无法区分率** = **全部可匹配样本**里，**无法给出最高值的结果**（最佳命中被 **≥2 个分类并列**、分不出该选哪一类）的占比（越低越好）。分母 = 全部可匹配样本（命中 + 无法区分 + 误判 = 可匹配样本数）——**与 D 的分母不同**，故 D + E 不一定等于 100%。E 告警色：≥50 红、≥20 黄。分类行的「查看详细」按钮**分列给出、各看各的**：**D 列（匹配正确率）**的按钮只列**匹配错误**样本（最佳命中唯一但不是自家，按被误判到的分类分组、条数多的组在前，每行「命中 x% · 自家 y%」＝ 与误判分类生成图／与自家生成图的匹配占比），**E 列（无法区分率）**的按钮只列**无法区分**样本（最高分被 ≥2 个分类并列，每行「并列 A、B · 最高 x% · 自家 y%」）；本列没有对应样本就不出现该按钮（另一列仍可单独打开），也**不再要求 D < 100%**——D 的分母已排除无法区分样本，可能出现「D = 100% 但仍有无法区分样本」。两个弹窗是**同一套版式**（同一个 `#vkDetailModal` 容器 + 同一组 `.xcard` / `.xmeta` / `.list` 样式，只有标题与说明段不同），且都**覆盖整页**（看不到身后的右栏与表格），故标题写明主体、标题下再用一行信息 chip 交代上下文：标题 = `匹配错误明细` / `无法区分明细` ` - <分类标注> ｜ <匹配动作>`，chip = `汇总图算法 <短名>`、`样本 N 张`、`匹配正确率 x%`（按 D 告警色）、`匹配正确个数 h / 能给出结果 k`、`匹配错误 w 张`、`无法区分率 y%`（按 E 告警色）、`无法区分个数 t / 可匹配样本 N`；下方说明段讲清本段各行的读法，单击缩略图看原图大图。执行模式的「详细分值」弹层同规：标题 `对照图分值 - <分类>`，chip = `本帧差异度 x%`、`对照图来源 <matchedFile>`，两处共用 `.xmeta` 样式。
- **不能生成有效产物的分类及其样本不进任何指标统计**：某分类没有该 kind 产物、或产物为全透明空图（缺注意区/点击区交集图、独有区图无独有点等）＝无判别点；明细行对应数值显示「——」，A 在产物无效时后端直接给 null。
- **覆盖范围统一**：每种 kind 都拿全部原图 × 全部分类比对，不按动作收窄。
- **结果完整缓存到 `resource/summary/verify.json`**（2026-09-12）：一次验证完整跑完（无中断）即把全部 kind 的结果**完整落盘** —— 五种指标 + 全部逐分类明细行 + 「查看详细」用的逐图明细（匹配错误 / 无法区分）一并写入（先写 `.tmp` 再原子改名，中途被杀只丢本次；文件可手删，随 `*.json` 一并被 git 忽略）。进程启动后首次访问本视图（或算法调优 `statOf()` 取值）时若文件存在就**完整恢复上次结果**，于是「**已标注（`resource/classify/` = 原图 + 标注 json + `data.json` 分类定义）与汇总分析（`resource/summary/` 全部产物与 `info.json`）的数据一个字都没变（指纹一致）」时界面直接显示「已计算」，**不必重算** —— 右栏统计行会多一行「已从 resource/summary/verify.json 恢复上次结果（数据没变即可直接用）」，明细页的完成时间 / 耗时 / 五张指标卡 / 明细表 / 「查看详细」弹窗全部照旧可用。反过来，只要这两处**有任何变动**（增删改原图 / 标注 / 分类定义，或产物 png 与 `info.json` 变化），指纹随之改变 → 恢复出来的结果立即标记为**过期**：左栏 chip 变琥珀「需重算」、右栏统计行追加「注意：已标注 / 汇总分析的数据有变动，需重新验证（N 种）」、并**弹一次提示**（2026-09-13 改为按「过期事件」去重：一次过期只在首次提示一次，数据重新一致、结果恢复「已计算」后再变动才会再提示 —— 旧版按「当前指纹」去重，而指纹在数据变动期间每 3 秒（`fp()` 的 TTL）就是个新值，同一次变动会被反复提示、历史日志跟着刷屏；提示固定放在「任务结束处理」之后，并给两处「已完成 · 仍过期」的完成提示记上「已提示」，不连弹两条同义消息）、明细页状态 chip 显示「已过期 · 需重算」；点「开始验证」重算即覆盖缓存。**另外每个 kind 逐图比对的原始分值（`[样本][分类]` 不匹配占比矩阵）单独缓存到 `resource/summary/verify-matrix.json`**（2026-09-12，见数据表那一行）：按「原图 / 产物各自的大小 + 修改时间」记账，没变过的整表 / 整行直接复用（连 PNG 都不解码），所以即使指纹变了、必须重算，也只会重算真正变过的那部分（例如刚重算过某个分类的产物，只会作废受影响的那些表）；右栏统计行只列一行「逐图比对结果缓存：resource/summary/verify-matrix.json。」（2026-09-13 起**只报文件名**，已载入的特征数 / 样本行数由运行中的进度行给出、不再重复），验证跑完后再补一行「其中直接复用逐图比对结果：N 条样本行 · M 种特征（没变过的图不重比）」。**「算法调优」用的就是同一份矩阵**，故「特征验证 → 算法调优 → 自动调整参数」连跑时一次都不必重复比对。
- 指纹在统计 `resource/classify/` 与 `resource/summary/` 全部文件（**相对各自分区根的路径** + 大小 + 修改时间 → hashCode，3 秒 TTL）时**排除 `verify.json` / `verify-matrix.json` / `opt-result.json` / `opt-weights.json` / `dedup-cache.json` 这些非产物数据文件**，并且**任何 `*.tmp` 一律排除**（2026-09-13）—— 写端统一「先写 `.tmp` 再原子改名」，`.tmp` 一定是写了一半的半成品（产物换新时它先出现、改名后又消失），计入只会让「汇总分析正在重写产物」的那几秒里指纹凭空抖动、把刚算完的验证结果误判成过期。排除这套缓存与半成品的理由：否则「写缓存 / 保存权重」这一步会反过来把自己判成过期（自动调整参数一落盘，验证结果就全变「需重算」）；而**产物本身**（`resource/summary/<分类>/*.png`、`info.json`）与 `resource/classify/` 的原图 / 标注变了，指纹**照旧**要变 —— 那才是真的「输入变了」。
- **指纹里不带绝对路径**（2026-09-13 修正，`VerifyService#appendTreeFiles`）：每行记的是`分区名/相对路径`（`classify/img_0001.png`、`summary/<分类>/same100.png`，分区名只为区分两棵树、不含盘符与上层目录），排序键同样用相对路径。指纹只回答「这批数据是不是同一份」，所以整个运行目录搬到别的盘 / 别的目录、分区根改名（如本次把 `classify/` 收进 `resource/classify/`）、换一个工作目录启动，只要文件本身（名字、大小、修改时间）没动，指纹就不该变。旧实现记的是 `Path#toString()`（**绝对路径**），搬一次目录就把全部 kind 判成「需重算」，白跑一轮；改完这一版后指纹格式变了一次，需要重新验证一轮，此后搬运不再影响。注意**文件名 / 相对路径仍然计入**：增删图、改名、换内容、把某张图挪到别的分类（归属变了）都照旧会变指纹。**升级这一次仍需重算一轮**（2026-09-13）：现有的 `verify.json` / `opt-result.json` 都是**搬迁之后没再算过**的旧缓存，里面记的指纹全部是按**搬迁前的绝对路径**算的，而文件已经不在那些路径上了 —— 新口径、旧口径都还原不出那个哈希，所以只能重算；好在**逐图比对矩阵（`verify-matrix.json`）与路径无关**（列 = 分类名 + 产物 size/mtime，行 = 原图文件名 + size/mtime），搬迁保留 mtime，所以这轮是**全部命中缓存、只重算汇总**，很快。此后搬运 / 改名都不再影响。
- 验证任务在后台单线程 + 并行流跑，页面停留该视图时 1 秒轮询进度。**进行中的进度行**（右栏进度条下的文字 + 本页 tips 行共用同一文案，前端 `vkTaskLine()`）用**逗号串联风格、不套括号**（2026-09-13 用户指定，同 3.2 去重那条）：`正在验证特征 1/54，当前特征名：红点提示，当前样本 12/847，已耗时 1 分 12 秒，已缓存 3 个特征，已缓存 2541 条样本比对行`——「当前特征名」= 正在算的 kind 短名（还没轮到具体特征时整段省略）、「当前样本」= 本 kind 已处理样本 / 该 kind 样本总数（总数未定时省略）、「已耗时」按后端 `task.startedMs` 逐秒走动、末尾两个「已缓存」= `resource/summary/verify-matrix.json` 当前的缓存规模（`matrixKinds` / `matrixRows`，为 0 时省略）。验证期间常驻缓存回收交给 JVM 的 GC（无任何手动清理入口），但两者都会长时间占用 CPU 与磁盘 IO，因此**不建议与执行模式的自动识别并行**。**本轮运行期间数据被改过**（保存标注 / 执行模式存样本 / 切进「汇总分析」触发自动重算产物…）会被记进 `task.dataChanged`（每个 kind 开始前用 3 秒 TTL 的 `fp()` 轻量比一次指纹、收尾再确认一次）：一旦为真，进度行末尾追加「期间数据已变动，本轮结果将标记为需重算」、右栏统计行追加完整说明、跑完再弹一条 warn 提示 —— 本轮结果算的确实是**变动之前**的数据，照实标成「需重算」，但把原因与下一步说清楚，不再让人看着「已完成」又变回「需重算」而以为白算（此时重跑很快：没变过的图直接复用逐图比对结果）。
- **左栏 chip 在运行中按本轮进度显示**（2026-09-13 用户反馈「点了开始验证，『已计算』的又变回『需重算』，看着像白算」之后改）：`已计算`（本轮已经算完它）/ `计算中…`（正在算它）/ `等待重算`（本轮还没轮到，灰色，与琥珀色的「需重算」区分开）—— **运行中不再出现「需重算」**（它是「等你点按钮」的语义，重算中显示它会让人以为这一轮没在算）；未跑时照旧只看结果状态：`已计算` / `需重算`（数据变了才变琥珀）。运行中同时**不再弹**那条「已标注 / 汇总分析的数据有变动，请重新验证」的一次性提示（原因改由进度行说明，见上一条），跑完按 `task.dataChanged` 决定提示文案：正常完成 = 绿色「结果已缓存（用时…）」，期间数据变动 = 琥珀「结果算的是变动之前的数据、已标记为「需重算」」。前端 `vkSig()` 的运行标签带上 `t.done`，保证每算完一个 kind 列表就重绘一次 chip。
- **按钮：运行中置灰，数据一变动就转绿**（2026-09-13 用户指定「默认是点了变灰的，但是如果发现了数据变动，就应该变绿」）：点「开始验证」后按钮**立即置灰禁用**（正在按最新数据验证，不必也不该再点；跑完自动恢复）；一旦发现**本轮运行期间样本 / 产物变动过**（前端按本轮 `task.startedMs` 认轮次、记下该轮开始时的 `fp` 指纹，与当前指纹不一致即算变动过；后端 `task.dataChanged` 同样算）→ 本轮结果注定作废，按钮**恢复亮绿**并提示「运行期间样本 / 产物发生了变动：这一轮算的是变动之前的数据 —— 点一下当场作废它，按最新数据重新开始」；点这个绿按钮 = **抢断式重跑**：新请求一进来就把正在跑的那一轮**当场作废**（它读的是变动前的样本 / 产物，跑完也没有意义）：后端递增 `runGen` 代次 + `interrupt()` 本轮线程（阻塞式 PNG 解码立刻退出，样本并行比对在检查点收手，最慢只多算当前这一张），被作废的那一轮**不落盘、不覆盖上次结果**，任务带 `superseded` 标记 → 右栏显示琥珀色「这一轮已被最新一次验证取代（数据已变动，按最新状态重跑）」，右下角同步一条 warn 提示（**不算失败**、也不用重试）。
- **顶栏（`.stagebar`）只写视图名「特征验证」**：进视图时由 `setStageTitle()` 显式重置（`#fname` = 视图名、`#fsub` / `#imgDims` 留空），否则会残留上一个视图（如汇总分析）的「分类 ｜ 动作 / 原始截图 N，分析产出 M」；样本库 / 已算口径统一由右栏 `#vkStat` 承担（该行 `white-space:pre-line`，恢复提示 / 需重算提示各占一行）。

### 3.5 算法调优（第 6 视图，组合特征成匹配算法）

建立在第 5 视图「特征验证」的结果之上：用 A/B/C/D 自动挑特征（E 只做展示、不参与挑特征）、组合成「匹配算法」，再逐张原图验证每个算法的分类匹配正确率。**前置条件**：先在「特征验证」跑完一次且样本 / 产物未变动（指纹一致），否则主图区提示先去完成特征验证。注意 D 的口径（2026-09-12 起）：分母只算「能给出结果」的可匹配样本（不含无法区分），所以 `D = 100%` 的含义是**没错判**、允许存在无法区分样本；本视图算法 2/3/4/5 的种子档位（D = 100% / D ≥ 90% / D ≥ 80% / D ≥ 70%）都跟着这个新口径走。本视图自己报告的「匹配正确率」同样在分母里剔除无法区分样本（2026-09-12 第三次修正：`命中 / (可判定样本 − 无法区分)`，无法区分不再算作判错），**与 D 的分母完全一致、数值可直接对比**；无法区分率 = `无法区分 / 可判定样本`，与 E 同口径（故两者之和不一定等于 100%）。

- **内置五种算法**（特征集合由验证结果自动组合，卡片里列出每个特征的入选依据；算法 1 的选品口径 = **(生成成功率 A − 无法区分率 E) × 匹配正确率 D 最大**，后四个都把这个「单一最佳」特征作为种子之一带上）：
  1. **单一最佳匹配特征** = 取「(A − E) × D」最大的一个特征，只用它判定（不再限制 A = 100%，A 与 E 已经在式子里面）；
  2. **单一最佳+100%正确率特征** = 上面那个最佳特征 + 全部 D = 100% 的特征；若它们的判定不能覆盖所有分类（某分类没有任何选中特征能正确判它），就对每个缺失分类补入「该分类匹配正确率最高」的特征，直到每个分类至少有一个特征能判定；补不满（某分类在所有特征下都没有有效产物）时卡片内给出橙色提示。
  3. **单一最佳+90+%正确率特征** = 最佳特征 + 全部 D ≥ 90%（**含 100%**）的特征，**补满口径与算法 2 完全一致**（缺失分类照样逐个补入该分类正确率最高的特征）。后端由 `buildBestSingleWith(lo=90, hi=∞)` 与算法 2 共用同一段实现，只是种子档位与文案不同。
  4. **单一最佳+80+%正确率特征** = 最佳特征 + 全部 D ≥ 80%（**含 100%**）的特征，同上（`buildBestSingleWith(lo=80, hi=∞)`）。
  5. **单一最佳+70+%正确率特征**（2026-09-12 新增）= 最佳特征 + 全部 D ≥ 70%（**含 100%**）的特征，同上（`buildBestSingleWith(lo=70, hi=∞)`）；档位更低、种子更宽，当没有 D ∈ [70%, 80%) 的特征时与算法 4 的特征集合完全相同（两行结果自然一致）。

- **打平（并列）处理**（与特征验证的 E 同口径）：① 逐张样本**逐特征**先查「该特征在这张样本上是否分不开」——某特征的最高匹配值被 **≥2 个分类并列**（分值一样、分不出该选哪一类）即视为该特征有问题，这张样本的加权平均里**整张放弃该特征**（对该样本全部分类一致移除，只改一半会变成两套口径）；② 放弃后重新加权，若最高匹配度**仍被 ≥2 个分类并列**（或本样本可用特征被全部放弃、无从判定），则给出**无法区分**的最终结论：既不算命中也不算判错，单独计入 `tie`（界面「无法区分率」）；③ 归属分类在本算法参与特征上没有**可判定的产物**（无有效产物，或产物存在但比对不了）的样本整张跳过、不进分母（同特征验证的「可匹配样本」口径）。全局匹配正确率 = 命中 /（可判定样本 − 无法区分）＝ 命中 /（命中 + 判错），**无法区分既不算命中也不算判错、不进它的分母**；无法区分率 = 无法区分 / 可判定样本（分母含无法区分）。命中 + 无法区分 + 判错 = 可判定样本，故正确率 + 无法区分率 不一定等于 100%。

### 3.6 执行模式（识别 + 点击）

切换过去即自动截图识别一轮并展示画面与结果，此后页面每 10 秒后台同步一次最新结果；点「立即识别」可手动单轮刷新。「开启自动识别」= 自动循环：每轮「截图识别 → 结果停留 3 秒供查看（可点按钮停止）→ 按下方所选方式执行点击 → 等 3 秒游戏响应」再进下一轮，运行中再次点击即停止。截图复用标注模式的找窗/调窗机制，**只用于识别与展示、不写盘**。

- **识别口径（只认 `resource/runtime/`）**：识别完全交给**算法调优落地的「综合最佳算法」**（`resource/runtime/algorithm.json` + `resource/runtime/<分类>/` 下该算法用到的产物），与 `resource/summary/` 的调优过程解耦。算法 = 若干**特征**（产物 kind + 基础分 X + 权重 Y），逐特征把当前帧与各分类在 `resource/runtime/<分类>/` 下的对应产物按既有逐图判据比对（**交集/多数/方框交集类**要求逐像素完全一致；**均值类**用逐通道容差 `execute.rgb-dist-threshold`，默认 255/3=85）得不匹配点占比，**匹配值 = 100 − 占比**；先放弃「最高匹配值被 ≥2 个分类并列（打平）」的特征（并列只在有有效产物的分类之间数：空图恒 0 分、不数进并列），再按 Σ「匹配值 × X × Y」÷ Σ「X × Y」算出各分类**匹配度**，**差异度 = 100 − 匹配度**。识别**不设阈值门槛**：匹配度唯一最高的分类即识别结果；最高被并列 = **无法区分**，本轮不动作并把并列的分类名称交代给页面（提示去算法调优调权重 / 补标注）。**没有 `resource/runtime/`**（从没跑过算法调优、或整目录被删）→ 不识别，直接提示「请先到『算法调优』完成一轮」。
- **依赖前提**：目标画面需先在标注模式打好标、跑过「汇总分析」，再跑一轮**算法调优**（「特征验证」→「刷新算法特征」，或直接「自动调整参数」）把综合最佳算法落地到 `resource/runtime/`；`resource/runtime/` 里缺该特征产物或尺寸不符的分类不参与比对。**算法调优每次跑完都会按「综合分 =（1 − 无法区分率）× 匹配正确率」最高的算法重刷 `resource/runtime/`**（也就顺手刷掉了执行与推荐用的算法）。
- **执行动作**：识别出「鼠标点击」动作后点「执行动作」，直接按右侧识别结果的坐标发送点击，**不再重新截图识别**（画面已变化请先点「立即识别」刷新结果）：
  - `post`（默认，后台消息）：向目标窗口投递完整点击消息序列，不要求窗口前台/可见、不抢占鼠标（游戏 / 模拟器多忽略合成消息，此时应切 `screen`）；
  - `screen`（前台点击）：`SetForegroundWindow + SetCursorPos + mouse_event` 真实输入（要求窗口可见不被遮挡）。
- 画面区实时帧上用**红白准星**叠加标出识别命中点（点击坐标），右栏展示识别结果与候选分类（差异度由小到大）。

## 六、已知限制 & 待办

- **抓窗限制**：WGC 无法直接抓 `WS_EX_LAYERED` 分层窗口（返回 `E_INVALIDARG`，业界通病）；仅当所有候选窗口都是分层窗时才降级为「显示器捕获 + 窗口矩形裁剪」——此时被遮挡部分会截到遮挡内容、移出屏幕部分被裁掉。
- 目标窗口在**其它虚拟桌面**时抓不到（API 限制）。
- 控制台输出中文乱码多为终端 GBK 显示问题（程序内部均 UTF-8）：先 `[Console]::OutputEncoding=[Text.Encoding]::UTF8` 再看日志。
- 多开多个相同目标程序时按标题取「面积最大」，暂无法指定具体实例。
- `resource/capture/` 持续落盘会积累：去重可挡静止/重复画面，长跑建议定期清理（`resource/classify/` 是要保留的样本；`resource/summary/` 可随时删除重算）。
- 识别对轻微光照 / 色偏 / 动态区域敏感，动态画面较多的分类需多采样本覆盖（后续方向：局部 ROI / 特征匹配）。
- 自动点击通过「开启自动识别」进行（每轮留 3 秒可停止的确认窗口）；尚无可配置的策略链（失败重试 / 条件分支等）与执行历史记录。

### B. 截图采集技术（为什么用 WGC）

需求是「**后台** + 抓 **GPU/DX 合成内容** + 多显示器缩放下坐标不偏移」地抓指定窗口——只有微软的 **Windows Graphics Capture**（WGC）满足（`Robot` 要窗口在前台、会截到遮挡层、缩放会偏；`PrintWindow` 对 GPU 分层窗口实测全黑）。因此用 C++/WinRT 写了个单文件采集器 `WindowsCapture.exe`（静态链接，与编译环境无关），Java 用 `ProcessBuilder` 调它：

```
WindowsCapture.exe --hwnd <句柄> --out <输出.bmp> [--timeout-ms 毫秒]
```

退出码分段：`0` 成功；`1xxxx` 参数错误；`2xxxx` 找不到窗口 / 分层 / 抓帧超时等窗口问题；`3xxxx` 内部异常。完整码表见 `native/windowcap/windowcap.cpp` 文件头注释（输出均为 UTF-8）。
